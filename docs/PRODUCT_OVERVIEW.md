# مرور محصول (Product Overview)

> این سند، منبع اصلی حقیقت (Source of Truth) برای مفهوم محصول، مدل داده‌ی مفهومی و معماری اطلاعات پروژه‌ی Quire-Clone است. سند [FRONTEND.md](./FRONTEND.md) و [BACKEND.md](./BACKEND.md) هر دو بر پایه‌ی همین سند نوشته شده‌اند. هرگونه تغییر در مفهوم محصول، ابتدا باید اینجا به‌روزرسانی شود و بعد در دو سند دیگر منعکس گردد.

## ۱. چشم‌انداز پروژه

یک نرم‌افزار مدیریت تسک (Task Management) شبیه به **Quire** است. تمرکز اصلی طراحی روی **نسخه‌ی موبایل** است (Mobile-first) با ناوبری پایین صفحه (Bottom Tab Bar) شامل ۴ تب اصلی:

1. خانه (Home)
2. تسک‌های من (My Tasks)
3. اعلان‌ها (Notifications)
4. حساب کاربری (Account)

## ۲. واژه‌نامه و مدل داده‌ی مفهومی

| اصطلاح | توضیح |
|---|---|
| **Workspace (فضای کاری)** | مفهومی چتری در صفحه‌ی خانه که لیست پروژه‌ها/سازمان‌های کاربر را نشان می‌دهد. یک Workspace می‌تواند حاوی یک Project یا یک Organization باشد. |
| **Organization (سازمان)** | واحد سازمانی که می‌تواند چند Project داشته باشد. هر Project دقیقاً به یک Organization متصل است (رابطه‌ی ۱ به N). دارای اعضا (Members) است. |
| **Project (پروژه)** | متعلق به یک Organization. دارای تسک‌ها، ستون‌ها (Columns/Status)، اعضای دارای دسترسی (زیرمجموعه‌ای از اعضای سازمان)، و چند نمای مختلف نمایش تسک. |
| **Task (تسک)** | واحد کاری در یک پروژه. دارای شناسه‌ی یکتا، عنوان، اعضا، برچسب، اولویت، توضیحات، پیوست، کامنت، تایمر و زیر-لیست (Subtask). |
| **Member (عضو)** | کاربری که در یک Organization عضو است؛ می‌تواند به صورت انتخابی به یک یا چند Project (Board) دسترسی داشته باشد. |
| **Notification (اعلان)** | رخدادهایی که برای کاربر ارسال می‌شود (تخصیص تسک، کامنت، تغییر وضعیت، درخواست تایید و ...). |

### رابطه‌ی موجودیت‌ها (Entity Relationships)

```
User ──< OrganizationMembership >── Organization ──< Project ──< Task ──< Subtask
                                                        │           │
                                                        │           ├──< Comment
                                                        │           ├──< Attachment
                                                        │           └──< TimeEntry (Timer)
                                                        │
                                                        └──< ProjectMembership >── User
                                                        └──< Column (وضعیت‌های سفارشی)

Task ──> Column (وضعیت فعلی تسک)
Task ──> User (Assignee)
Task ──> Tag (چند به چند)
Task ──< Follower >── User (چند به چند — کاربرانی که از تغییرات تسک باخبر می‌شوند)
Task ──> Favorite (وضعیت «مورد علاقه»‌ی کاربر جاری روی همین تسک)
Task ──< TaskActivityEntry (لاگ رویدادهای خودِ همان تسک — نه نمودار تجمیعی)
Notification ──> User (گیرنده)
Notification ──> Task/Project/Organization (موجودیت مرتبط)
ActivityLog ──> User + Organization/Project (برای نمودار فعالیت روزانه)
```

> **نکته:** `TaskActivityEntry` (لاگ رویدادهای یک تسک، مثل «یونس روی این تسک کار می‌کند») مفهومی جداست از `ActivityLog` بالا — آن یکی فقط داده‌ی تجمیعی روزانه برای نمودارهای Heatmap (سازمان/پروژه/کاربر) است و به تسک خاصی وصل نیست؛ `TaskActivityEntry` یک فید متنیِ رویدادها مخصوص یک تسک است و در صفحه‌ی جزئیات تسک نمایش داده می‌شود.

جزئیات دقیق فیلدها و جداول در [BACKEND.md](./BACKEND.md) بخش «مدل داده» آمده است.

## ۳. معماری اطلاعات (۴ تب اصلی)

### تب ۱ — خانه (Home)

صفحه‌ی اصلی، با پیام خوش‌آمدگویی به نام کاربر و تعداد تسک‌های **در حال انجام** او (لینک به تب «تسک‌های من»)، و زیرش لیست Workspace های کاربر (هر Workspace شامل یک Project یا یک Organization است). با کلیک روی هر سازمان، پروژه‌های آن به‌همراه **درصد پیشرفت** هرکدام (سهم تسک‌های تکمیل‌شده از کل تسک‌های همان پروژه) باز می‌شود.

#### صفحه‌ی سازمان (Organization Overview)

با کلیک روی یک سازمان وارد صفحه‌ی Overview آن می‌شویم که شامل:

- عنوان سازمان، تاریخ ساخت سازمان، و لیست اعضا (اواتارهای روی‌هم‌افتاده، با کلیک قابل مدیریت)
- **خلاصه‌ای از پروژه‌ها**: هر پروژه با نوار پیشرفت (درصد تسک‌های تکمیل‌شده) و لینک به صفحه‌ی همان پروژه؛ امکان افزودن پروژه‌ی جدید
- **آخرین فعالیت‌ها**: فید رخدادهای اخیر سازمان (فعلاً پیاده‌سازی نشده و همیشه خالی نمایش داده می‌شود)

#### صفحه‌ی پروژه (Project)

صفحه‌ی پروژه دو بخش اصلی دارد:

**بخش List:**
لیست تسک‌های پروژه که با چند ساختار نمایشی متفاوت قابل مشاهده است:

- **Tree** (درختی — تسک و زیرتسک‌ها)
- **Board** (کانبان — با قابلیت Drag & Drop بین ستون‌ها)
- **Table** (جدولی)
- **Timeline** (خط زمانی)
- **Calendar** (تقویمی)

امکانات این بخش:
- ساخت و ویرایش ستون‌های Board (Column Management)
- افزودن کاربر به پروژه (انتخاب از میان اعضای سازمان که دسترسی به این Board پیدا می‌کنند)

**صفحه‌های افزودنی (Custom Pages):**
کنار تب‌های «لیست» و «نمای‌کلی» یک دکمه‌ی «+» هست که با آن می‌شود صفحه‌ی جدیدی به همان صفحه اضافه کرد:

- **سند (Document)**: یک صفحه‌ی خالی که کاربر می‌تواند در آن متن بنویسد.
- **چت (Chat)**: صفحه‌ای برای گفتگوی کاربران.

**بخش Overview:**
- تعیین تاریخ شروع و پایان پروژه
- پیوست فایل (Attachment) به سطح پروژه
- **Project Health**: نمایش وضعیت تسک‌ها در دسته‌های Active / Completed / Due in period / Overdue + نمودار زمانی روند تغییرات این دسته‌ها
- **Task Status Distribution**: نمودار دایره‌ای (Pie Chart) بر اساس وضعیت ستون‌ها (To Do / In Progress / Completed)
- **Deadline Calendar**: تقویم ماهانه که سررسید تسک‌های همان روز را نشان می‌دهد
- **Member Activity**: نمودار فعالیت روزانه‌ی اعضا (شبیه گیت‌هاب)، مشابه همان مفهوم در سطح سازمان اما مختص همین پروژه

#### مدل تسک (Task)

هر تسک شامل:

| فیلد | توضیح |
|---|---|
| نام (Name) | عنوان تسک |
| شناسه‌ی یکتا (ID) | مثل `#324` |
| Assignee | مسئول تسک |
| Follower (دنبال‌کننده) | یک یا چند نفر از اعضای پروژه که تسک را دنبال می‌کنند؛ در صفحه‌ی جزئیات تسک با یک آیکون کنار اولویت مدیریت می‌شود و وقتی کاربر جاری هم دنبال‌کننده باشد آیکون به رنگ برند پر می‌شود |
| Favorite (مورد علاقه) | یک قلب toggle-پذیر که کاربر جاری می‌تواند تسک را «مورد علاقه» علامت بزند |
| Add Date | تاریخ شروع، تاریخ سررسید، و تکرار (هیچ/روزانه/هفتگی/ماهانه) |
| Tag | برچسب — از میان برچسب‌های ازقبل ساخته‌شده انتخاب یا برچسب تازه ساخته می‌شود |
| Start Timer | تایمر کارکرد روی تسک؛ مجموع زمان صرف‌شده در صفحه‌ی جزئیات تسک («زمان صرف‌شده») نمایش داده می‌شود |
| Description | توضیحات |
| Attachment | فایل پیوست |
| Comment | بحث/گفتگو |
| Priority | اولویت (بازتاب رنگی روی آیکون) |
| Sublist | زیر-تسک‌ها (Subtasks) |
| Activity Log | فید متنی رویدادهای همین تسک (مثل «یونس روی این تسک کار می‌کند») — رجوع به یادداشت بالا |

#### ساخت تسک جدید (New Task)

در تب‌های «خانه» و «تسک‌های من» یک دکمه‌ی گرد شناور (FAB) به رنگ برند با آیکون «+» در گوشه‌ی پایین‌سمت‌راست صفحه (بالای Bottom Tab Bar) وجود دارد. کلیک روی آن کاربر را به **صفحه‌ی ساخت تسک جدید** می‌برد.

فرم ساخت تسک شامل فیلدهای اولیه‌ی مدل تسک است: عنوان، پروژه‌ی مقصد (اجباری، چون هر تسک به یک پروژه تعلق دارد)، مسئول (Assignee، از میان اعضای سازمانِ همان پروژه)، تاریخ سررسید، اولویت، برچسب و توضیحات. بقیه‌ی امکانات تسک (پیوست، کامنت، تایمر، زیر-تسک) بعد از ساخت و در **صفحه‌ی جزئیات تسک** انجام می‌شوند، نه در فرم ساخت.

### تب ۲ — تسک‌های من (My Tasks)

تمام تسک‌هایی که به کاربر تخصیص داده شده و **فقط تسک‌های در وضعیت «در حال انجام»** قابل مشاهده هستند؛ با همان نماهای Tree/Board/Table/Timeline/Calendar.

بخش **Overview** این صفحه شامل:
- نام، عکس پروفایل، ایمیل، توضیحات، فایل‌های پیوست‌شده‌ی کاربر
- **Attention Required**: تسک‌هایی که نیاز به رسیدگی فوری دارند
- **Task Status Distribution**: پراکندگی وضعیت تسک‌های خود کاربر (To Do / Completed / ...)
- **Project Health**: مشابه مفهوم سطح پروژه، اما تجمیع‌شده برای همه‌ی پروژه‌های کاربر
- **Portfolio Activity**: نمودار فعالیت شبیه گیت‌هاب، مختص خود کاربر

### تب ۳ — اعلان‌ها (Notifications)

لیست اعلان‌ها با فیلتر بالای صفحه: **All / Unread / Read / Approval**. با کلیک روی هر اعلان، کاربر به صفحه‌ی مرتبط (تسک/پروژه/سازمان) هدایت می‌شود؛ با کلیک روی **نام عامل رخداد** (کسی که آن اعلان را ایجاد کرده)، کاربر به پروفایل عمومی همان شخص هدایت می‌شود (نام، نقش، سازمان‌ها، فعالیت).

### تب ۴ — حساب کاربری (Account)

تنظیمات حساب کاربری و دکمه‌ی خروج (Logout).

## ۴. نقشه‌ی راه فاز اول (Phase 1 Scope)

مطابق تصمیم فعلی پروژه:

- **فقط فرانت‌اند** با Next.js پیاده‌سازی کامل می‌شود (رابط کاربری کامل، حتی اگر بخشی از داده‌ها Mock باشد).
- **بک‌اند** بسیار ساده و مبتدی، با **Django** و پایگاه داده‌ی **SQLite** نوشته می‌شود؛ صرفاً برای فراهم کردن یک API واقعی و ساختار داده‌ی درست — نه برای مقیاس یا عملکرد.
- داده‌های واقعی اهمیتی ندارند و ممکن است در آینده پاک/بازنشانی شوند؛ آنچه مهم است **ساختار درست** کد و مدل داده است تا مهاجرت بعدی به یک سیستم حرفه‌ای‌تر (مثلاً Postgres + معماری مقیاس‌پذیرتر) بدون بازنویسی اساسی ممکن باشد.

جزئیات فنی این تصمیم در [FRONTEND.md](./FRONTEND.md) و [BACKEND.md](./BACKEND.md) آمده است.
